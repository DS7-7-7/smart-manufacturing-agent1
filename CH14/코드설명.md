# 제14장 코드 동작 구조 설명

제조 주문 처리 Agent 시스템이 **어떻게 서로 맞물려 돌아가는지**를 정리한 문서입니다.
"자연어 주문 → LLM 분석 → Tool 호출 → 비즈니스 규칙 판단 → ERP DB 반영"의
전체 흐름을 파일 단위로 따라갑니다.

---

## 1. 폴더 구조

```text
CH14/
├── src/                     # 파이썬 파일 (여기서 실행)
│   ├── 01_init_db.py
│   ├── 02_seed_data.py
│   ├── 03_erp_models.py
│   ├── 04_llm_models.py
│   ├── 05_erp_tools.py
│   ├── 06_business_rules.py
│   ├── 07_order_agent.py
│   ├── 08_workflow.py
│   ├── 09_run_agent.py
│   ├── 10_exception_handler.py
│   └── 11_api.py
└── data/
    └── erp.db               # 01_init_db.py 가 자동 생성
```

> 파일명이 숫자로 시작해서 파이썬 일반 `import`가 안 되므로,
> 파일끼리는 `importlib.import_module("03_erp_models")` 방식으로 서로를 불러옵니다.

## 2. 계층(Layer) 구조 — 무엇이 무엇에 의존하는가

코드는 아래에서 위로 쌓이는 4개 계층으로 되어 있습니다.
**위 계층은 아래 계층만 호출하고, 반대 방향 호출은 없습니다.**

```text
┌─────────────────────────────────────────────┐
│  진입점 계층                                    │
│   09_run_agent.py (콘솔)   11_api.py (HTTP)   │
└───────────────┬─────────────────────────────┘
                │ 호출
┌───────────────▼─────────────────────────────┐
│  Agent / Workflow 계층                         │
│   07_order_agent.py   08_workflow.py          │
│   10_exception_handler.py                     │
└───────────────┬─────────────────────────────┘
                │ 호출
┌───────────────▼─────────────────────────────┐
│  판단 계층                                      │
│   06_business_rules.py                        │
└───────────────┬─────────────────────────────┘
                │ 호출
┌───────────────▼─────────────────────────────┐
│  데이터/Tool 계층                               │
│   05_erp_tools.py                             │
│   03_erp_models.py  04_llm_models.py          │
│   01_init_db.py     02_seed_data.py           │
└───────────────┬─────────────────────────────┘
                │ 읽기/쓰기
        ┌───────▼───────┐
        │  data/erp.db  │
        └───────────────┘
```

핵심 원칙은 **역할 분리**입니다.

| 계층 | 담당 | 대표 파일 |
| --- | --- | --- |
| 진입점 | 사용자 입력 받기 | 09, 11 |
| Agent | 자연어 이해·작업 계획 (LLM) | 07, 08 |
| 판단 | 돈과 직결된 의사결정 (규칙) | 06 |
| 데이터 | DB 조회·변경 | 03, 04, 05 |

> **LLM은 "무엇을 할지 계획"만 하고, "재고·생산·발주 결정"은 06번 규칙이 합니다.**
> LLM이 임의로 발주를 넣는 사고를 막기 위한 구조입니다.

## 3. 파일별 역할 요약

| 파일 | 한 줄 역할 | 핵심 산출물 |
| --- | --- | --- |
| `03_erp_models.py` | DB에 저장되는 데이터 구조 (SQLAlchemy) | 11개 테이블 클래스 |
| `01_init_db.py` | 03번 모델로 실제 DB 파일 생성 + 세션 관리 | `data/erp.db`, `get_session()` |
| `02_seed_data.py` | 실습용 초기 데이터 입력 | P300, BOM, 공급업체 |
| `04_llm_models.py` | LLM이 주고받는 데이터 구조 (Pydantic) | OrderRequest 등 스키마 |
| `05_erp_tools.py` | Agent가 쓰는 ERP 함수 모음 | get_/create_ 함수 |
| `06_business_rules.py` | 재고·생산·발주·결제 판단 규칙 | decide_order() |
| `07_order_agent.py` | LLM 호출 + 전체 처리 절차 | process_order() |
| `08_workflow.py` | 07의 절차를 그래프(분기)로 재구성 | LangGraph WORKFLOW |
| `09_run_agent.py` | 콘솔에서 주문 입력받아 실행 | main() |
| `10_exception_handler.py` | 부분결제·긴급주문 예외 처리 | handle_payment/urgent |
| `11_api.py` | 위 기능을 HTTP API로 노출 | FastAPI app |

### 03번 vs 04번 — 헷갈리기 쉬운 부분

두 파일 다 "model"이지만 뜻이 다릅니다. (둘 다 **LLM 엔진 자체가 아닙니다**)

```text
03_erp_models.py  →  DB에 "저장되는" 데이터의 틀   (SQLAlchemy)
04_llm_models.py  →  LLM이 "주고받는" 데이터의 틀   (Pydantic)
```

실제 LLM 엔진(Qwen/GPT) 정의와 호출은 **07번**에서 합니다.

## 4. 데이터 흐름 — "P300 500개 주문" 한 건이 처리되는 과정

```text
사용자: "신제품 P300 500개 주문해줘"
    │
    ▼  ① 자연어 분석 (07: analyze_order → LLM 또는 mock)
OrderRequest(product_name="P300", quantity=500, priority="normal")
    │
    ▼  ② 제품 확인 (05: get_product)
{product_id:"P300", name:"신제품 P300", unit_price:50000}
    │
    ▼  ③ 주문 생성 (05: create_order)
주문 #1 생성, 금액 2,500만원, 결제상태 unpaid
    │
    ▼  ④ 재고 조회 (05: get_inventory)
가용 100개, 부족 400개
    │
    ▼  ⑤ 판단 (06: decide_order)
    │     - 재고 100 < 500      → 400개 생산 필요
    │     - BOM 확인: Motor 100 부족, Case 200 부족
    │     - 결론: action = "purchase" (구매 후 생산)
    │
    ▼  ⑥ 실행 (05: create_purchase_order × 2 + create_production_order)
Motor 100개 @ S001 발주
Case  200개 @ S003 발주
생산계획 #1 (400개) 등록 → 주문 confirmed
    │
    ▼
ERP DB 반영 완료
```

### 의사결정 분기 (06번 decide_order)

```text
재고 충분?
 ├─ YES ────────────────────────→ action = "ship"   (전량 출고)
 └─ NO → 부족분 생산 필요
          자재(BOM) 충분?
           ├─ YES ──────────────→ action = "produce" (바로 생산)
           └─ NO ───────────────→ action = "purchase"(발주 후 생산)
```

## 5. 실행 경로 2가지 — Agent vs Workflow

같은 일을 하지만 표현 방식이 다릅니다. 결과는 동일합니다.

### (A) 07번 Order Agent — 절차적(순차 실행)

```text
process_order(text)
  → analyze_order()          # 분석
  → get_product()            # 제품 확인
  → create_order()           # 주문 생성
  → get_inventory()          # 재고 조회
  → decide_order()           # 판단
  → if ship:    update_order_status("shipped")
     else:      create_purchase_order() + create_production_order()
```

### (B) 08번 LangGraph Workflow — 상태 기계(그래프)

```text
START → analyze → validate → check_stock
                                  │
                     [branch_stock]
                     ├ shortage<=0 → ship → END
                     └ shortage>0  → calc_shortage
                                        │
                              [branch_produce]
                              ├ produce  → production → END
                              └ purchase → purchase → production → END
```

- **Agent(07)**: 코드로 if/else를 직접 씀 → 읽기 쉬움
- **Workflow(08)**: 분기를 그래프의 노드/엣지로 명시 → 복잡한 흐름 확장에 유리

두 경로 모두 내부적으로 **05번 Tool과 06번 규칙**을 똑같이 사용합니다.

## 6. LLM 백엔드 전환 구조 (07번 핵심)

`07_order_agent.py`의 `_llm()` 래퍼 하나만 LLM을 다루고,
**환경변수 `LLM_BACKEND` 로 엔진을 갈아끼웁니다.** 나머지 10개 파일은 안 바뀝니다.

```text
LLM_BACKEND=mock   →  LLM 없이 정규식 파싱 (API/키 불필요, 실습·테스트용)
LLM_BACKEND=qwen   →  로컬 vLLM  (http://localhost:8001/v1)   ← 기본값
LLM_BACKEND=gpt    →  OpenAI API (OPENAI_API_KEY 필요)
```

동작 방식(공통):

```text
_llm(system, user, schema)
  → OpenAI SDK 로 요청 (base_url/api_key 만 백엔드별로 다름)
  → schema 주면 JSON(구조화 출력)으로 파싱
  → 실패 시 3회 재시도 (미지원 파라미터는 빼고 재시도)
  → 그래도 실패하면 mock 파싱으로 폴백
```

> 이 구조 덕분에 "어떤 모델을 넣어도 다른 코드에 영향 없음"이 성립합니다.
> Qwen·GPT 모두 OpenAI 호환 인터페이스라 같은 코드로 부를 수 있기 때문입니다.

## 7. 예외 처리 (10번) — 정상 흐름에 끼어드는 안전장치

정상 주문과 별개로, 실제 업무의 예외를 규칙과 승인 절차로 처리합니다.

### 7.1 부분 결제

```text
결제 상태 확인 (06: check_payment)
 ├─ paid            → 진행
 └─ partial/unpaid  → 주문 보류(on_hold) + 승인 요청
                      → 관리자 승인 시 confirmed 로 복귀
```

### 7.2 긴급 주문

```text
생산 CAPA 확인 (06: check_urgent_capacity)
 (일 생산능력 200개 기준, 필요일수 = 올림(수량 / 200))
 ├─ 납기 내 가능  → 긴급 생산 진행
 └─ 납기 초과     → 관리자 승인 필요
```

핵심은 **Agent가 임의로 진행하지 않고, 규칙 판단 → 승인 절차를 거친다**는 점입니다.

## 8. 진입점 (09번 콘솔 / 11번 API)

같은 Agent/Workflow를 두 가지 방식으로 노출합니다.

```text
09_run_agent.py  (콘솔)
    입력: 키보드로 자연어 주문
    출력: 처리 로그를 화면에 출력

11_api.py  (HTTP)
    Client → FastAPI → Agent/Workflow → Tool → DB
    POST /orders            구조화 주문   {"product":"P300","quantity":500}
    POST /orders/nl         자연어 주문   {"text":"P300 500개 주문"}
    POST /orders/workflow   워크플로 실행
    GET  /inventory/{pid}   재고 조회
    POST /seed              DB 초기화
```

## 9. 실행 순서 정리

```bash
cd src

# 1) DB 준비 (최초 1회)
python3 01_init_db.py        # data/erp.db 생성
python3 02_seed_data.py      # 초기 데이터 입력

# 2) 실습 (mock = API 없이)
LLM_BACKEND=mock python3 09_run_agent.py             # 콘솔 Agent
LLM_BACKEND=mock python3 09_run_agent.py --workflow  # LangGraph
LLM_BACKEND=mock python3 10_exception_handler.py     # 예외 처리

# 3) API 서비스
LLM_BACKEND=mock uvicorn 11_api:app --reload --port 8000
# → http://localhost:8000/docs
```

## 10. 한눈에 보는 전체 그림

```text
                사용자 자연어 주문
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
  09 콘솔 진입점                  11 API 진입점
        └──────────────┬──────────────┘
                       ▼
         07 Order Agent  /  08 LangGraph Workflow
              │  (자연어 이해·작업 계획 = LLM)
              ▼
         06 Business Rules
              │  (재고·생산·발주·결제 = 규칙 판단)
              ▼
         05 ERP Tools
              │  (조회·생성 = DB 접근)
              ▼
     03 모델 · 01 DB · 02 시드
              ▼
          data/erp.db

  ※ 04 LLM 스키마: 07↔06 사이 데이터 형식 담당
  ※ 10 예외처리: 결제·긴급 상황에서 06 규칙 + 승인 절차 개입
```

정리하면, 제14장 코드는 **"LLM은 계획, 규칙은 결정, Tool은 실행"** 이라는
역할 분리 위에서 자연어 주문 한 문장을 실제 ERP 데이터 변경까지 이어주는 구조입니다.
