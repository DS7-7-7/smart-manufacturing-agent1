# 자율 주문 처리 및 생산 관리 Agent — 작동 방식 & 설계 방식

제14장 종합 실습으로 구현한 제조 주문 처리 Agent 시스템의
**설계 방식(왜 이렇게 만들었나)**과 **작동 방식(어떻게 돌아가나)**을 정리한 문서.

---

## 1. 한 줄 요약

> 자연어 주문을 입력받아 **LLM Agent가 제품을 식별**하고, **비즈니스 규칙이 재고·생산·구매를 판단**하며,
> ERP Tool을 호출해 **주문 → 재고 확인 → 발주서 자동 작성 → 생산계획**까지 수행하는 제조 Agent 시스템.

---

## 2. 설계 철학 — 역할 분리

이 시스템의 가장 중요한 설계 원칙은 **"누가 무엇을 결정하는가"의 분리**다.

```text
LLM(Agent)      →  이해와 판단   : 자연어 해석, 제품 식별, 작업 계획
Business Rules  →  의사결정      : 재고·생산·구매·결제 판단 (돈과 직결)
ERP Tools       →  실행         : DB 조회 및 데이터 변경
```

**왜 나눴는가?**
LLM은 자연어를 유연하게 이해하지만 100% 신뢰할 수는 없다(숫자 오독, 없는 값 생성 등).
그래서 "재고가 충분한가", "얼마를 발주할까" 같은 **돈이 걸린 결정은 규칙이 담당**하고,
LLM은 "사용자가 무엇을 원하는지 이해"하는 역할만 맡긴다.

이 원칙이 코드 전반에 일관되게 적용되어 있다.

## 5. 데이터 모델 두 종류 (혼동 주의)

두 파일 다 "model"이지만 뜻이 다르다. **둘 다 LLM 엔진 자체가 아니다.**

```text
03_erp_models.py  →  DB에 저장되는 데이터 구조   (SQLAlchemy)
04_llm_models.py  →  LLM이 주고받는 데이터 구조   (Pydantic)
```

실제 LLM 엔진(Qwen/GPT) 정의·호출은 `07_order_agent.py` 에서 한다.

## 6. 제품·부품 구성 (부품 공유)

완제품 4종이 부품을 **공유**한다. → 한 부품이 부족하면 여러 제품 생산에 영향.

```text
RC700 로봇청소기 = 구동모터 + 메인보드 + 본체케이스
AP200 공기청정기 = 팬모터   + 메인보드 + 필터×2 + 본체케이스
HF100 무선선풍기 = BLDC모터 + 제어보드 + 날개 + 배터리팩
VC500 무선청소기 = 구동모터 + 제어보드 + 배터리팩 + 본체케이스

공유 부품:
  구동모터   → RC700, VC500
  메인보드   → RC700, AP200
  제어보드   → HF100, VC500
  본체케이스 → RC700, AP200, VC500
  배터리팩   → HF100, VC500
```

## 7. 작동 방식 — 주문 한 건의 처리 흐름

입력: `"신제품 로봇청소기 500개 주문해줘"`

```text
① 주문 분석 (07: analyze_order)
    자연어 → {제품명:"로봇청소기", 수량:500, 우선순위:normal}
    · LLM이 추출하되, 수량은 규칙으로 교차검증 (오독 방지)
        ↓
② 제품 식별 (07: identify_product)   ← 핵심 설계
    LLM 판단 → 규칙 검증 → 폴백 → 되묻기
    "로봇청소기" → RC700 확정
        ↓
③ 주문 생성 (05: create_order)
    주문 #1, 결제 unpaid 상태로 등록
        ↓
④ 재고 조회 (05: get_inventory)
    가용 100개 → 400개 부족
        ↓
⑤ 판단 (06: decide_order)
    재고 부족 + 부품 부족 → action = "purchase"
        ↓
⑥ 실행
    부족 부품 발주 (05: create_purchase_order)
      + 발주서 작성 (12: 콘솔 출력 + txt 저장)
    생산계획 생성 (05: create_production_order)
    주문 확정 (05: update_order_status → confirmed)
```

### 의사결정 분기 (06: decide_order)

```text
재고 충분?
 ├─ YES ───────────────→ ship     (전량 출고)
 └─ NO → 부족분 생산 필요
          부품(BOM) 충분?
           ├─ YES ──────→ produce  (바로 생산)
           └─ NO ───────→ purchase (발주 후 생산)
```

## 8. 제품 식별 방식 (핵심 설계)

원래 "제품 식별"은 자연어 이해 영역이므로 **Agent(LLM)가 담당**하도록 설계했다.
규칙은 뒤에서 검증·폴백하는 보조 역할이다.

```text
identify_product(text):
  ① (LLM 모드) DB 제품 목록을 LLM에게 제시
        "사용자가 말한 게 이 중 무엇이냐?"  → product_id 선택
        ↓
  ② LLM이 고른 코드를 DB로 검증
        · 실제 존재하면 확정 (LLM이 지어낸 코드 방지)
        ↓
  ③ 실패 시 규칙(resolve_product) 문자열 매칭 폴백
        · 대소문자·구분자·띄어쓰기 무시 (rc700, RC-700, 로봇 청소기)
        · mock 모드는 항상 이 경로
        ↓
  ④ 그래도 못 찾으면 → 후보 목록과 함께 "되묻기"
```

**되묻기 예시**

```text
"청정기 300개 주문"  → 특정 불가
  어떤 제품인지 알려주세요:
    1. 로봇청소기 RC700
    2. 공기청정기 AP200
    3. 무선선풍기 HF100
    4. 무선청소기 VC500
  → "2" 입력 → 공기청정기로 처리
```

> 실제 LLM(qwen/gpt) 모드에서는 "청정기 = 공기청정기"를 문맥으로 이해하므로
> 되묻지 않고 바로 처리된다. 되묻기는 LLM·규칙 모두 확신 못 할 때의 안전장치.

## 9. LLM 백엔드 전환 방식

`07_order_agent.py` 의 `_llm()` 래퍼 하나가 LLM을 담당한다.
**환경변수 `LLM_BACKEND` 로 엔진을 교체**하며, 나머지 파일은 바뀌지 않는다.

```text
LLM_BACKEND=mock   →  LLM 없이 규칙 파싱 (API/키 불필요, 실습용)
LLM_BACKEND=qwen   →  로컬 vLLM (http://localhost:8001/v1)
LLM_BACKEND=gpt    →  OpenAI API (OPENAI_API_KEY 필요)
```

동작: OpenAI SDK로 요청 → json_schema로 구조화 출력 →
3회 재시도(미지원 파라미터 제거) → 실패 시 mock 파싱 폴백.

**신뢰성 장치** — LLM이 수량을 잘못 읽어도(500→50) 문장의 실제 숫자로 교차검증해 보정한다.

## 10. 실행 경로 2가지 (결과 동일)

### (A) Order Agent — 절차적 (07)

```text
process_order() : analyze → identify → create_order
                → get_inventory → decide → 실행(출고/발주/생산)
```

### (B) LangGraph Workflow — 상태 기계 (08)

```text
START → analyze → validate → check_stock
                                 │
                      [재고 충분?]
                      ├ YES → ship → END
                      └ NO  → calc_shortage
                                 │
                          [생산 가능?]
                          ├ produce  → production → END
                          └ purchase → purchase → production → END
```

두 경로 모두 내부적으로 **같은 05 Tool과 06 규칙**을 사용한다.

## 11. 예외 처리 (14.6)

정상 흐름과 별개로, 실제 업무 예외를 규칙+승인 절차로 처리한다.
`10_exception_handler.py` 단독 실행으로 확인한다.

### 부분 결제

```text
결제 상태 확인
 ├─ paid            → 진행
 └─ partial/unpaid  → 보류(on_hold) + 승인 요청
                      → 관리자 승인 시 confirmed
```

### 긴급 주문

```text
생산 CAPA 확인 (일 생산능력 기준 필요일수 계산)
 ├─ 납기 내 가능  → 긴급 생산 진행
 └─ 납기 초과     → 관리자 승인 필요
```

핵심: **Agent가 임의로 진행하지 않고 규칙 판단 → 승인 절차를 거친다.**

## 12. 발주서 작성 (방법 A)

발주가 결정되면 DB 기록에 더해 사람이 읽을 발주서를 만든다.
`12_purchase_order.py` 가 담당하며, **실제 전송은 하지 않는다.**

```text
create_purchase_order() (DB 기록)
        ↓
build_po_document()     (발주서 텍스트 생성)
        ↓
① 콘솔 출력
② data/purchase_orders/PO-0001_S001.txt 저장
```

발주서 내용: 발주번호·일자·공급업체·품목·수량·단가·금액·납품기한.

## 13. 실행 방법

```bash
cd src

# DB 준비 (최초 1회 또는 초기화)
python3 01_init_db.py
python3 02_seed_data.py

# 주문 처리 (mock = API 없이)
LLM_BACKEND=mock python3 09_run_agent.py             # 콘솔 Agent
LLM_BACKEND=mock python3 09_run_agent.py --workflow  # LangGraph
LLM_BACKEND=qwen python3 09_run_agent.py             # 실제 Qwen

# 예외 처리 확인 (14.6)
LLM_BACKEND=mock python3 10_exception_handler.py

# 발주서 작성 단독 확인
python3 12_purchase_order.py

# API 서비스
LLM_BACKEND=mock uvicorn 11_api:app --reload --port 8000
# → http://localhost:8000/docs
```
